# Backend reference

What the schema looks like once provisioned, and what each server function accepts and
returns. The SQL that creates all of this lives in `assets/sql/`; the functions live in
`assets/edge-functions/`. Deploy every function with JWT verification **off**, since they
authenticate with a password in the request body.

## Table: `public.feedbacks`

| Column | Type | Null | Default | Role |
|---|---|---|---|---|
| `id` | bigint identity | no | generated | Primary key. The watcher matches this against its local ledger |
| `reviewer_name` | text | no | | Reviewer name |
| `section` | text | no | | The section commented on, plain name without a prefix |
| `comment` | text | yes | | The feedback text. Optional when there is audio |
| `audio_path` | text | yes | | Path to the audio file in the bucket |
| `user_agent` | text | yes | | Reviewer's browser, used to tell two people with the same name apart |
| `created_at` | timestamptz | no | `now()` | Orders the engine's queue |
| `project` | text | see note | | Scope: which project |
| `material` | text | see note | | Scope: which material |
| `type` | text | no | `'comment'` | One of `comment`, `conclusion`, `decision` |

**About nullability of scope columns:** on a fresh install (sequence A) `project` and
`material` are NOT NULL, because there is no legacy data. On a migrated backend
(sequence B) they are nullable, so HTML published before the migration keeps working.

The column names are in Portuguese because changing them would break every backend
already running this schema. They are the wire format, not user-facing text.

## Security model

This is the part worth understanding before trusting the setup, because it is what makes
publishing a public key safe.

**Two independent layers.** A grant decides whether a role may touch the table at all; a
row-level policy decides which rows it may write. Both are required. A policy without a
grant produces "permission denied for table", which reads like a policy bug and is not.

**The anonymous role can insert and nothing else.** No select policy exists for anonymous
visitors, so the public key in the page cannot read a single row, not even the reviewer's
own. Reading always goes through a server function that requires the password.

**The insert policy validates on the server.** Field lengths, the allowed set of types,
and the rule that a row must carry text or audio are enforced by the database, not just
by the browser. Client-side validation is a convenience; the constraint is what makes it
true.

## Storage bucket

A **private** bucket for reviewer audio, with an upload-only policy for anonymous
visitors, a 15 MB size cap, and an allowlist of audio content types. Private means the
files cannot be read by URL: the dashboard receives short-lived signed URLs generated by
the server function.

The bucket name is parameterizable. Change it in all three places in
`02-bucket-storage.sql` and in the kit's `BUCKET_AUDIO` placeholder.

## Table: `public.painel_config`

Holds the dashboard password when you are not using an environment secret. Row-level
security is **on with no policies at all**, which means anonymous visitors cannot read
it, cannot write it, and cannot discover that it exists. Only the service role, meaning
the server functions, can see it.

## Server functions

### `read-feedback`

| | |
|---|---|
| Request | `POST { "password": "...", "project"?: "...", "material"?: "..." }` |
| Filtering | Scope fields are optional. Without them it returns everything |
| Response 200 | `{ "feedbacks": [{ id, reviewer_name, section, comment, audio_path, created_at, type, project, material, audio_url? }] }` |
| `audio_url` | A signed URL valid for two hours, present only when there is audio |
| Ordering | Newest first |
| Wrong password | 401 |
| Password not configured | 500, with an instruction pointing at both configuration paths |

Password resolution: the environment secret wins; the config table is the fallback.

### `clean-orphans`

| | |
|---|---|
| Request | `POST { "password": "..." }` |
| What it does | Lists files in the bucket, matches them against `audio_path` values, and deletes only files with no matching row |
| Response 200 | Counts and the names of what was removed |

Run it after closing a review. Orphans happen when an upload succeeds and the database
insert then fails, which the kit's ordering makes rare but not impossible.

### `record-decision`

Writes a row of type `decision`, which is how the engine tells the dashboard that a
structural item is waiting for a human. Validates that scope fields are present and
within length, and that the comment is non-empty.

### `approvals`

Three actions in one function: `registrar` records the owner's verdicts on structural
items, `listar` returns the pending ones, and `marcar` flags them as consumed. This is
the channel that carries a decision from the browser back to the machine running the
watcher.

Forging an approval would require the password, which the anonymous insert route in the
page does not have.

## Verifying a deployment

Always test the **wrong** password first:

```bash
curl -s -X POST "<EDGE_FN_URL>/read-feedback" \
  -H "Content-Type: application/json" -d '{"password":"wrong-on-purpose"}'
```

A 401 here is the result you want. A function that answers 200 to a bad password is
protecting nothing, and finding that out now costs a minute, while finding out later
costs whatever was in the database.

Then repeat with the real password and confirm a 200 with the expected fields present.
